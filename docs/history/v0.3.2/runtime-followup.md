# Capsid v0.3.2 independent follow-up review
> This is the review as recorded at the time. The [v0.3.2 acceptance record](README.md) documents subsequent fixes, retests and outstanding checks.
## 1. Verdict at review time

**Verdict at this revision: block the working-tree merge and v0.3.2-beta release.** All three earlier P0 causes were fixed and this review found no new P0. Four P1 findings remained. Three reproduced against the production library and the fourth had a reachable thread interleaving. Consequences included guaranteed pool capacity falling to zero, a freed slot remaining unavailable to another application, and requests queuing or being rejected despite an available worker.

The review covered `dev/v0.3.2` on 2026-11-23 at `85b9e1e` plus uncommitted changes. The Windows tree had 44 modified tracked files, with 3,441 insertions and 907 deletions. Line numbers refer to that tree. [Review brief](review-brief.md) · [Earlier review](runtime-review.md) · [Stable and prerelease identities](../../reference/release-status.md)

### P1 findings

1. **After a scale-out attempt fails, an active pool with `minReady=1` can remain at zero READY workers.** While the second worker in a two-slot pool is inside the factory, health recycling removes the only guaranteed floor worker; because a startup is already in flight, the recovery controller marks the floor slot `needs_replacement`. When the second startup fails, the failure branch sets the scale-out target to zero, and only the successful installation branch checked for pending `needs_replacement` slots. After the failure callback returns, the probe observes `ready=0, calls=2, scale_in_flight=0` with no 3rd startup attempt scheduled to restore the floor until new traffic arrives. An active pool should check for floor-replacement deficits on both failure and success paths while preserving backoff and quarantine budgets, and acceptance should assert automatic recovery without new traffic. [Waiting for replacement 870–880](../../../src/host/generation_pool.cc#L870) · [Recovery decision 352–365](../../../src/host/worker_recovery.cc#L352) · [Failure settlement 1529–1565](../../../src/host/generation_pool.cc#L1529) · [Success settlement 1598–1612](../../../src/host/generation_pool.cc#L1598)

2. **After health-driven recycling removes the guaranteed worker, the surviving worker still occupies an elastic slot.** Both machine slots are in use (1 guaranteed + 1 elastic READY). Reclaiming the guaranteed worker through the supervisor's health-recycle entry yields `ready=1, elastic=1, peer=0`, blocking a second application from acquiring the vacated slot. Health recycling checked only `elastic_held` on the victim slot instead of reusing the floor-transfer settlement used by LRU and natural exit. Reuse that settlement under the pool lock and return the freed quota once outside the lock; tests should assert that a peer application can acquire the slot. [Health recycling 518–535](../../../src/host/generation_pool.cc#L518) · [Settlement 1364–1383](../../../src/host/generation_pool.cc#L1364) · [Supervisor call 265–270](../../../src/host/worker_supervisor.cc#L265)

3. **During dispatch-lease handoff to `kBeginRequest`, the eviction thread can misclassify a continuously busy worker as idle.** Starting from `pending=1, inflight=0`, the eviction thread reads `inflight=0`; the I/O thread then submits the request (`inflight` becomes `1`) and releases the lease (`pending` drops to `0`); the eviction thread next reads `connection_owners=0` and `pending=0`, treating the worker as idle and issuing shutdown even though the executor was never idle. Because each counter is an independent atomic, TSan passes cleanly despite this race. Maintain one continuous occupancy count from lease acquisition to request completion (or synchronize handoff with idle checks) and add a barrier-controlled test asserting the request receives a complete response. Derived from source interleaving; no request drop was observed in this round. [Idle check 281–291](../../../src/host/worker_executor.h#L281) · [Submit 240–249](../../../src/host/worker_executor.cc#L240) · [Handoff 1635–1637](../../../src/host/managed_listener.cc#L1635) · [Eviction 783–818](../../../src/host/generation_pool.cc#L783)

4. **HTTP dispatch picks the lowest combined-load worker first and checks only its HTTP cap.** With a per-worker HTTP limit of 1, worker A holds an active HTTP lease while worker B has a free HTTP slot but a higher combined score due to connection/queued bytes (`client_bytes_loader` = 2). The probe observes `ready=2, second_lease=0, at_max=1`, queuing or rejecting the second request. Filter READY workers with spare HTTP capacity before ranking by load, reporting `at_max` only when all READY candidates are at their HTTP cap, and assert the second request dispatches to B. [Selection & admission 386–447](../../../src/host/generation_pool.cc#L386) · [Load score 297–306](../../../src/host/worker_executor.h#L297) · [Listener 758–769](../../../src/host/managed_listener.cc#L758)

### P2 findings

1. **Two scale-down replacements can simultaneously commit the same switching margin.** `workersTotal=4, surgeWorkers=3`. A and B each have two guaranteed workers, and one replacement is reserved for each. Both reservations are submitted in sequence. If both reservations are successful, the measured value is `steady=2, surge=4`. The reservation checks for the larger values of both old and new, but only the smaller new pool size is recorded. Currently, the production Admin performs the deployment serially, so this counterexample directly proves that the concurrency contract of the ledger itself is invalid. It has not been proven that two online Admin requests can overlap. During the reservation process, the required surge difference after the switch is also retained. Abort and commit processes each settle the corresponding commitments. [Reserve 60–93](../../../src/host/worker_capacity_ledger.cc#L60) · [Submission 101–127](../../../src/host/worker_capacity_ledger.cc#L101) · [Admin Serial Boundary 644–650](../../../src/host/main.cc#L644)

2. **Workers that have already started recycling but are still alive will disappear from the soft water level statistics.** The pool snapshot exports this PID, and the `async_reaping_retired` flag is set. Monitoring will skip it directly before accumulation, and this will continue in the next round. For example, with a high water level of 85 MiB, other processes have 80 MiB, and processes that have not yet been evicted have 40 MiB. In the next round, they will be returned early at 80 MiB. There is a separate sampling path for hard access. The distinction between "still occupying memory" and "already selected as eviction targets" is made. In the next round, the measurement will be based on the actual amount, and the objects being recycled will never be selected again. [Snapshot 740–754](../../../src/host/generation_pool.cc#L740) · [Monitoring 626–663](../../../src/host/eviction_coordinator.cc#L626) · [Access Re-sampling 569–581](../../../src/host/eviction_coordinator.cc#L569)

3. **Enabling the `on_worker_started` callback leaks wakeup descriptors across cold-start/stop cycles.** Adding a no-op `on_worker_started` callback to the three-round Linux cold-start test raised open process fds from `4` to `10` and timed out waiting for reclamation. The pump thread retained strong references to exited executors in `observed_retired_` until generation drain. While production `main` does not set this callback, callers that enable it accumulate descriptors; track stable IDs or weak references and close/destroy exited executors promptly so both modes return to baseline fds. [Reclamation 1183–1205](../../../src/host/generation_pool.cc#L1183) · [Final release 1684–1695](../../../src/host/generation_pool.cc#L1684) · [Existing fd test 976–1007](../../../tests/test_host_elastic_pool.cc#L976)

4. **The `QuotaExceededError` exported by the current Profile cannot be structured cloned.** In the Windows actual worker, calling `structuredClone` on instances with the message `x`, `quota=10`, and `requested=20` will throw a `DataCloneError`, with the message `unsupported object class`. The Web IDL defines serialization and deserialization steps for this class. The existing cloning mechanism in the runtime should be utilized, supporting nested objects and duplicate references. It is necessary to check the constructor, message, code, two values, and the default null. Both APIs in the exported table are available. [Constructor 23–65](../../../js/dom-exception.js#L23) · [Profile Export Table](../../../js/profile-manifest.js#L63) · [Clone Entrance 17–25](../../../vendor/txiki.js/src/js/polyfills/structured-clone.js#L17) · [Web IDL Interface Contract](https://webidl.spec.whatwg.org/#quotaexceedederror)

5. **There are three additional observable deviations in the Web IDL numerical values and Web Crypto parameters compared to the actual implementation.** In the actual worker, passing `quota: -0` results in `Object.is` returning false for negative zeros. If the `getRandomValues` parameter is omitted or an ordinary object is passed, a `TypeMismatchError` is actually thrown, as the IDL binding requires a `TypeError`. A `Uint8Array` with a length of 1 and a `byteLength` property of 65537 will also be incorrectly rejected due to exceeding the quota. Limited double conversions should retain the sign; the view type and byte length should be obtained from the native view information. The `TypeMismatchError` for valid floating-point views and the `QuotaExceededError` for truly excessive integer views have both passed this round of testing. [double conversion 15–21](../../../js/dom-exception.js#L15) · [Crypto Implementation 60–83](../../../js/bootstrap.js#L60) · [Web IDL double](https://webidl.spec.whatwg.org/#es-double) · [Web Crypto Algorithm](https://w3c.github.io/webcrypto/#Crypto-method-getRandomValues)

6. **The old Host/App configurations are still available as production entries, and soak itself relies on them.** The actual v1 documentation will be included in the v1 schema, and the applications and host configurations generated by soak are also v1. The design document limits the reasons for retaining the old configurations to old regression tests, which are different from running code and the first line of AGENTS.md. Examples, fixtures, and soak inputs that still use the old format should be changed to v2, and the production assignments of these two old schemas should be removed, with tests rejected for the old versions being replaced. `binding-v1` and C ABI v7 have independent contracts. There is also an internal call branch for the activation plan, which releases the preheated elasticity account immediately when returning a warm worker; it is necessary to inventory the actual callers before retiring this entry. [Configuration Allocation 894–903](../../../src/host/config.cc#L894) · [soak input 453, 487](../../../tests/soak/run_managed_soak.py#L453) · [Design 520](../../design/config-v2.md#L520) · [Internal Call Branches 997–1009](../../../src/host/managed_host.cc#L997)

7. **Two generation digests in the eviction coordinator tests omit the `sha256:` prefix required by the recovery controller.** Both fixtures constructed bare 64-hex digests while `active_state` / `worker_recovery` require a `sha256:` prefix, causing health recycling to fail with `lifecycle phase and document are inconsistent`. With a valid `sha256:` prefix, P1 #2 reproduced cleanly with zero controller rejection. Update both fixtures to valid `sha256:` digests and assert recovery scheduling. [Fixtures 357–370, 1430](../../../tests/test_host_eviction_coordinator.cc#L357) · [Digest check 67–77](../../../src/host/active_state.cc#L67) · [Controller 62–77](../../../src/host/worker_recovery.cc#L62)

### P3 suggestions

1. **There is still an assertion that depends on time estimation for the qualification and drain tests.** The qualification thread indeed has a barrier to enter the callback, and there are assertions for the final state. However, the main thread waits for 50 ms to determine whether the pump has had a chance to end early. Under slow scheduling, this observation may still be valid even if the protection against early termination is removed. Instead of sleeping, use a signal that the pump thread has actually performed a dequeue check once to replace the sleep. Keep the existing quotas, callback counts, and final state assertions. [Tests 907–929](../../../tests/test_host_elastic_pool.cc#L907)
2. **Windows directory race condition testing only involves renaming between two directory identities.** The test indeed requires both renaming and successful read operations to verify usability. All configurations that can be successfully read still originate from the same directory, and `pair-ok` cannot distinguish between two different identities. No directory out-of-bounds conditions or sandbox bypassing were observed in this round of testing. The test aims to produce a distinguishable result for the legal pairing of two different identities, and to verify the relationship between sub-file handles and the fixed parent directory on a supported file system. [Windows Cases 481–531](../../../tests/test_host_local_capsid_policy.cc#L481) · [Parent Identities and Child Openings 411–449](../../../src/host/local_dev_host.cc#L411)
3. **The gate can detect hash errors, but it fails to detect the total number of categories.** The received list states that there are 13 historical plans or logs, but counting each line reveals 14 items, and the gate still passed. After this review, the list has been corrected to 15 items. The gate can summarize the number of rows by kind and compare it with the counts to avoid further drift.
