# Capsid v0.3.2 managed runtime review
> This is the review as recorded at the time. The [v0.3.2 acceptance record](README.md) documents subsequent fixes, retests and outstanding checks.
**Verdict at this revision: block the mainline merge and the v0.3.2-beta release.** A normal WebSocket upgrade let the listener read a destroyed request record. Scale-down and retirement had separate lifetime defects. Two counterexamples were independently executable: the Host let an application exceed its declared resident limit, and deployment could claim a slot when all machine-wide slots were already occupied.

The review covered four core commits in `dev/v0.3.2`, `a7fd47e..e44d6ad`, spanning 122 files with 14,068 insertions and 14,813 deletions. Source line numbers refer to `e44d6ad`. Working-tree HEAD `85b9e1e` added one documentation commit. The two numerical configuration and ledger counterexamples were observed in execution. The other findings followed from source control flow. [Release history and recorded measurements](../../reference/release-status.md)

## P0 blockers

### 1. A successful WebSocket upgrade reads a destroyed request record

`pending` references elements in `requests_`. The upgrade branch preserves sessions and leases, registers WebSocket, and then executes `requests_.erase(it)`. However, the next line copies from the same `pending` to `pool`. References become invalid when elements are deleted. A normal 101 upgrade can enter this branch without thread contention. Behavior is undefined, which may cause the Host to crash. The strong references to the pool can be removed along with sessions and leases before deletion; the order of `finalize_request` in the same file is correct. Introduce a commit for `c060e78`. [Upgrade Branch 1654–1698](../../../src/host/managed_listener.cc#L1654) · [Existing implementations: 2324–2328](../../../src/host/managed_listener.cc#L2324)

### 2. A pool can destroy a slot before scale-up admission returns

`request_scale_out` first marks the slots and adds `replacements_scheduled_`. After unlocking, it enters the capacity callback phase. At this point, no background thread has been initiated, so `replacements_in_flight_` can still be zero. If the cold pool is also evicted at the same time, the pump enters `finalize_drain` to clear `slots_`. Both successful and failed branches subsequently access the old subscript directly. Strong references held by the pool only extend the lifespan of the pool object; they cannot preserve elements that have been cleared. At the beginning of the function, locking was still in place before reading `slots_.size()`.

Place the slot into the lock, and let the drain wait for the execution of the qualification operation to be completed, or verify the pool state and whether the slots are still valid after the callback returns. The obtained elastic quota must be accurately returned once more along the cancellation path. Do not call the coordinator with the pool lock. Introduce the commit `d02a60e`, and see the coordinator integration in `e44d6ad`. [Reservation and Return Paths 510–623](../../../src/host/generation_pool.cc#L510) · [drain End Condition 945–949](../../../src/host/generation_pool.cc#L945) · [Clearing slots 1522–1539](../../../src/host/generation_pool.cc#L1522)

### 3. The Host accepts maximums.pool.minReady without enforcing it

The schema allows `maximums` and `defaults` to share a pool structure containing `minReady`. The model derives this value, but when assembling the Host strategy, only the maximum pool size and other fields are passed. The compiler ultimately only checks that `effective_min <= effective_max`. This violates the configuration consumption red line in the review guidelines.

Run the parser and compiler using the `e44d6ad` Host library of WSL2: The Host sets `maximums.pool={minReady:1,maxWorkers:4}`, and the App requests `{minReady:3,maxWorkers:4}`. The actual output is `max.minReady=1 compiled=1 effective.minReady=3`. It is recommended to pass this value to the final effective policy check, covering the fixed pool shorthand, the flexible pool, and inheriting default values. Such a Host configuration can truly define the application's permanent commitment. Introduce commit `d02a60e`. [Schema 703–711, 800–802](../../../src/host/config.cc#L703) · [Model Mapping 1009–1016](../../../src/host/host_config_model.cc#L1009) · [Strategy Compilation 203–259](../../../src/host/policy_compiler.cc#L203)

## P1 findings

### 4. Scaling up before deployment can exceed the machine-wide worker budget

`try_acquire_elastic` will deduct steady-state and used elastic slots; the reverse `reserve_fresh` only deducts steady-state and excess surges. `reserve_replace` also omits the elastic occupation for the steady-state check after the switch. Setting the total amount to 2 and surge to 0 in the actual ledger, application A occupies 1 steady-state and 1 elastic slot, while reserving 1 steady-state slot for B, resulting in `reserve_b=1 steady=2 elastic=1`. The entire counterexample is valid in a single-threaded environment. Apart from this gap, the `minReady=0` deployment will actually preheat 1 process after reserving 0 slots, and only attempt to occupy it at the time of adoption.

Unify the accounting within the existing ledger for new deployments, replacements, steady-state conditions, and preheating overlap periods. First, allocate resources for the actual processes to be launched, then initiate them. If the preheating fails or verification is completed, release the resources according to their category. For elastic slots that can be reclaimed, hand them over to the existing coordinator for re-reservation. Related submissions include `d02a60e` and `e44d6ad`. [Ledger 15–60, 159–177](../../../src/host/worker_capacity_ledger.cc#L15) · [Reservation and Preheating 3045–3083](../../../src/host/managed_host.cc#L3045) · [adoption 519–535](../../../src/host/main.cc#L519)

### 5. Deployment and recovery can bypass tenant quotas

Taking `maxWorkers=2` as an example, tenant A has 1 guaranteed minimum and 1 elastic worker in service. When tenant B deploys 1 guaranteed worker, the total number of guaranteed workers is 2, and the first check passes. In reality, 3 workers are needed. The second check fails because no idle candidates are found, and the loop is broken, yet the function still returns a success. When there is spare capacity, tenant B can start up when the number of workers reaches 3. Even if space is freed, there is no reservation between the deployment check and the registration of a new pool, allowing sibling applications to scale during the warm-up period.

The same entry does not check the memory used by tenants at all. When `hardMemory` is set to a single value, a successful return is directly given, even if the usage of existing processes has reached the threshold. A new guaranteed minimum Worker can still be started. This entry is called during both hosting deployment and startup recovery. It is recommended to reserve the required slots for tenants before preheating. If the slots are not sufficient after recycling, return the existing reasons for rejection, and settle the reservation upon submission or failure. For tenants that have reached the memory threshold, the runtime access rules continue to apply. When recovering a zero-resident pool, the required slots should be calculated as 0 based on their actual preheating number. Submit `e44d6ad`. [Deployment Check 131–189](../../../src/host/eviction_coordinator.cc#L131) · [Run-time checks 260–297](../../../src/host/eviction_coordinator.cc#L260) · [Restoration 3574–3606](../../../src/host/managed_host.cc#L3574)

### 6. Routine scale-down retains exited executors and wakeup descriptors

Every scale-down operation moves the executor into `retired_`. The pump performs a join on the retired items and marks them as `joined`, but retains their strong references. Each round also scans historical entries. The container is cleared only when the entire generation is retired. On POSIX, the event source of each executor holds a pair of wake-up descriptors until the event source is destroyed. An application that remains online and repeatedly wakes up from zero and scales down back to zero can have the number of child processes return to zero, while the number of descriptors and objects on the Host continues to grow.

The completion conditions for recycling should include the consumption of the last batch of events, the release of the listener's reference to the executor identity, and the thread's joining. If these conditions are met, the item is released. Deleting the item directly after joining would conflict with the bare pointers saved by the current listener. First, correct the ownership of the delegate and callback, then remove the historical objects. Related commits: `d02a60e`, `e44d6ad`. [Add to retirement queue 723–731, 990–999](../../../src/host/generation_pool.cc#L723) · [join 1070–1090](../../../src/host/generation_pool.cc#L1070) · [Final Cleanup 1533–1545](../../../src/host/generation_pool.cc#L1533) · [Waking Descriptor 31–59](../../../src/host/worker_event_source.cc#L31)

### 7. A selected worker is unprotected until its request starts

After receiving the raw pointers from `pick_worker`, the listener still needs to process queues and request headers. It is not until `submit(kBeginRequest)` that the executor increases the inflight count. During this period, the reaper or coordinator can still observe idle states and submit shutdowns. Subsequently, begin can enter an executor that has already shut down, with no rejection results for the submitted interfaces, and the listener does not reassign tasks before sending. The impacts include HTTP requests that should have been processed and upgrade handshake failures. The conclusion is that the order of dispatching and shutting down conflicts, and the established WebSocket has an independent connection occupancy count.

Let the selection also acquire short-term request occupancy, and release it when the begin takes over or the assignment is canceled. Eviction and drain check the same occupancy; re-selection is only performed for requests that have not yet been sent, to avoid duplicate execution of business logic. Envoy's connection pool also binds requests when connections are available and updates the schedulable status based on flow occupancy. Related commits: `c060e78`, `d02a60e`, `e44d6ad`. [Select 387–428](../../../src/host/generation_pool.cc#L387) · [Idle Check and Shutdown 699–727](../../../src/host/generation_pool.cc#L699) · [Distribution: 724–757, 1597–1599](../../../src/host/managed_listener.cc#L724) · [Submission 217–247](../../../src/host/worker_executor.cc#L217) · [Envoy Connection Pool](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/connection_pooling)

### 8. Process samples can remain stale when only a tenant memory quota is configured

When there is no readable Worker cgroup, memory access reads the PID cache with `force_refresh=false`. The cache does not have a timestamp. The background refresh thread will not start unless the tenant's `hardMemory` is set, or the global `checkInterval` is set to zero. Even if a process exceeds the threshold after its first sampling, subsequent scale-out can still be allowed with the old smaller value; the old larger value will continue to reject requests incorrectly. Similarly, periodic cleanup of PID paths that have been evicted will not run if only tenant quotas are configured.

To give the process sampling a clear freshness, and to clear the identity upon process exit. The minimum fix should allow the access path without background refresh to be refreshed as needed, while maintaining the existing cgroup reading and process sampling implementation. Submit `e44d6ad`. [Cache 87–110, 125–133](../../../src/host/memory_sampler.cc#L87) · [Tenant Sampling 205–235](../../../src/host/eviction_coordinator.cc#L205) · [Background Enable Conditions 539–559](../../../src/host/eviction_coordinator.cc#L539)

### 9. Draining processes leave memory accounting too early

When switching versions, the old pool is first deregistered by the coordinator, and then enters the drain phase. Workers with ongoing tasks can continue to exist until they are emptied or expire. The water level calculation only considers the ready slots in the active pool, and even processes that have just received a shutdown signal and are still being asynchronously recycled are not included. If the old generation still occupies memory, the expansion of the new generation may pass a budget check. This error is particularly noticeable during the long connection blue-green switch.

"Process should still be measured" and "Can be considered for eviction". Retain the memory statistics of the old processes and the recycling process until the actual exit. Scheduling and eviction still only access the active slots that meet the criteria. Submission `e44d6ad`. [Version Switch 676–687](../../../src/host/main.cc#L676) · [Pool Snapshots 650–670](../../../src/host/generation_pool.cc#L650) · [Total calculation: 299–315, 432–457](../../../src/host/eviction_coordinator.cc#L299)

### 10. The last worker can retain an elastic slot after a guaranteed slot is evicted

The pool has 1 guaranteed worker and 1 elastic worker, with `minReady=1`. If the guaranteed worker remains idle for too long, the pool allows eviction to select it, but only releases the elastic worker when the victim slot is marked with `elastic_held`. In reality, there is only 1 worker left in the pool, but the ledger still holds 1 guaranteed worker and 1 elastic slot. When other pools request capacity, this pool is already at the guaranteed limit and cannot be evicted to reclaim additional slots.

It is possible to transfer the guaranteed minimum identity to the remaining Worker within the same pool lock, and return the flexible quota outside the lock. The idle timeout and memory eviction should share this settlement rule. Submit `e44d6ad`, and refer to `d02a60e` for the idle timeout path. ## P2 findings

### 11. Denied startup admission fails to notify queued cold requests

The failure to start the factory will trigger `on_scale_out_failed_`. Earlier startup requests can also fail, for example, when the permission queue is full. This path calls `abandon()`, returns the slot, and wakes up the condition variable of the pool, but the failure event is not delivered to the listener. If cold requests have been enqueued and are waiting for this startup, and there are no other events, it will default to waiting for the queue to timeout and receiving a 504 error. This has delayed known startup failures into queue timeout. Let the two failure paths share a notification outside of the lock, as the listener already has logic to check whether other Workers are ready or still starting. Submit `d02a60e`. [License Rejection and Cleanup 1300–1352](../../../src/host/generation_pool.cc#L1300) · [Factory Failure Notifications 1399–1419](../../../src/host/generation_pool.cc#L1399) · [Queue Failure Handling 1398–1424](../../../src/host/managed_listener.cc#L1398)

### 12. Opening configuration and entry files by path leaves the application directory unpinned

The local entry point only allows ordinary file names. POSIX reading also checks the file type, owner, and length before allocation. The `O_NOFOLLOW` protection is applied to the final component. Reading configurations and bundles re-parse the parent directory from the path. If the application directory is replaced between two openings, configurations and programs from different directories can be read. Windows's checks on the reparse point cannot guarantee that the same parent directory is used for both reads. The impact is limited to local development workspaces where directories are allowed to be replaced.

When starting up, fix the application root directory handle. The configuration and bundle are all opened relative to this identity, reusing the directory handle pattern already present in the project hosting state directory. For explicitly specified independent host configurations, adopt their own required trust boundaries. Commit `1910e64`. [Local opening and file inspection 161–234](../../../src/host/local_dev_host.cc#L161) · [Two reads of the configuration and bundle 804–823, 848–886](../../../src/host/local_dev_host.cc#L804) · [Repository Directory Handle Usage 196–208](../../../src/host/managed_host.cc#L196)

### 13. The design document mixed up single-worker PSSs with density-related experiments.

The design includes a combined estimate of 7.2–8.2 MiB and "2 GiB can accommodate 700+". If each instance is charged at this cost, 2048 MiB would correspond to approximately 249–284 full instances, without deducting Host costs. The original records provide different experiments: the single Worker PSS for programs of 10, 100, and 1024 KiB were 7.2, 8.2, and 16.0 MiB, respectively; independent 2 GiB density experiments measured the number of hot instances at 715, 496, and 127, respectively. It is recommended to directly quote both sets of records and their submissions, to avoid operational issues where the density of the smallest program is used for applications of 1 MiB. This is an issue of consistency in the design baseline. [Design Comparison Table Line 405](../../design/config-v2.md#L405) · [Single Worker Measurement](../../reference/benchmarks.md#L61) · [Density measurement](../../reference/benchmarks.md#L108)

## Verified paths and compliance with review standards

The mailbox delivers work to the I/O thread and releases the mailbox lock before processing the running queue. The monitoring thread joins outside the monitoring lock. The above path does not form a reverse lock cycle; item 2 is an issue of validity period for object states before and after unlocking.
