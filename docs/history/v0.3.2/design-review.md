## Release blockers at the reviewed revision

### P1 · Running processes lack a shared tenant `hardMemory` ceiling

Section 8 calls for a kernel-enforced tenant ceiling via `memory.max`, including long-lived connections. At this revision, deployment and scale-up summed tenant memory samples and attempted an idle replacement within the tenant or refused admission once the tenant reached its limit. The background task refreshed samples when only a tenant quota was configured. Each managed worker received a leaf cgroup directly beneath the configured root with its own effective `memoryMax`. Sibling applications and workers had no shared tenant parent ceiling. Between admission checks, existing workers could grow beyond the intended limit. [Design §8](../../design/config-v2.md#L441) · [Deployment](../../../src/host/eviction_coordinator.cc#L244) · [Scale-up](../../../src/host/eviction_coordinator.cc#L520) · [Background sampling](../../../src/host/eviction_coordinator.cc#L749) · [Worker startup](../../../src/host/managed_host.cc#L296) · [Cgroup creation](../../../src/host/worker_cgroup.cc#L51)

This conclusion comes from execution-path verification. Real cgroup scenarios have proven that a worker's `memory.current` can be read. Qualification should also verify that two applications under the same tenant and two generations during a rolling switch share one enforced quota, while another tenant remains independent. In a non-delegated cgroup environment, the guarantees that can be provided must be stated explicitly. [Existing cgroup cases](../../../tests/test_host_eviction_coordinator.cc#L1556)

### P1 · A tenant within its share can lose its only warm worker

Section 7.2 allows global LRU only when **all active tenants** are within their soft share. When computing shares, all active tenants are counted, but when checking whether any tenant exceeds its share, only the evictable worker candidate set is scanned. If an over-share tenant holds only protected/guaranteed workers, it disappears from that second check. The single-eviction path under capacity contention shares the same flaw. [Design Section 7.2](../../design/config-v2.md#L422) · [Watermark eviction](../../../src/host/eviction_coordinator.cc#L675) · [Capacity contention](../../../src/host/eviction_coordinator.cc#L384)

The independent probe used real pools, workers, the coordinator, and metrics, injecting only memory readings. The budget was 100 MiB with 85/75 MiB watermarks. Tenant A had one guaranteed worker, tenant B had one idle elastic worker, and each had a 50 MiB share.

| Tenant A / B memory | Design expectation | Observed watermark scan |
| --- | --- | --- |
| 45 / 45 MiB | Both within share; evicting B via global LRU is valid. | Evicted 1; A/B READY count 1/0; reason correct. |
| 80 / 10 MiB | A is over share (with only protected workers); keep B even if the low watermark is not reached immediately. | B was evicted in all three independent runs (A/B READY 1/0); B's `global_lru` counter incremented by 1. |

Qualification should verify that both inputs yield their expected outcomes across both watermark eviction and capacity contention. If reclaiming memory takes priority over protecting small tenants, Section 7.2 must be updated explicitly. [Independent probes](probes/design_probes.cc) · [Existing two-phase test](../../../tests/test_host_eviction_coordinator.cc#L795)

### P1 · Inheriting `jsHeap` can silently raise an explicit `worker.memoryMax`

The Host defaults to `memoryMax=96MiB` and `jsHeap=64MiB`. When the application is configured with `memoryMax=72MiB`, schema, type parsing, and strategy compilation all succeed, resulting in 72/64 MiB. Even when the application declaration is changed to 32 MiB, the three steps still succeed, ultimately yielding **64/64 MiB**. The compiler takes the maximum value of the declared memory and heap limits, which is then used during the managed startup. This violates the rule specified in Section 2.3, which prioritizes using the explicit values declared by the application for each field. This example only compiles the configuration without allocating the corresponding memory. [Field Evaluation Rules](../../design/config-v2.md#L81) · [Strategy Compilation](../../../src/host/policy_compiler.cc#L675) · [Quota Transfer](../../../src/host/managed_host.cc#L296)

During qualification, compatible 72/64 combinations must remain valid as originally defined. For conflicting combinations, if both values cannot be fulfilled simultaneously during runtime, a clear error should be returned before deployment. Accepted configurations must adhere to the stated upper limits. Existing field consumption tests examine changes in individual fields and their impact on models or effective strategies. However, these tests must also cover cross-field inheritance. [Existing field consumption tests](../../../tests/test_host_config_model.cc#L472) · [Independent Qualification Assertions](probes/design_probes.cc)

## Test results and performance evidence

- **Design-related CTest:** Rebuilt and ran selected config, policy, capacity-ledger, elastic-pool, eviction, deployment, listener, and recovery tests. Windows passed 37/37. WSL2 Linux registered 52 cases and passed 51 as an unprivileged user (skipping the delegated cgroup test), then passed the delegated cgroup test with privileges (reading `17,321,984` bytes). These counts cover only the design-review selection. [Cgroup test](../../../tests/test_host_eviction_coordinator.cc#L1556)
- **Configuration and queue defaults:** Both minimal and full Host and App examples extracted directly from the design passed production schema validation and parsing. An application declaring only `minReady=0, maxWorkers=8` compiled on an 8-worker Host to queue size `64`, queue timeout `5000 ms`, and idle timeout `60000 ms`. Cross-field inheritance counterexamples are recorded above. [Design examples](../../design/config-v2.md#L95) · [Cold-start defaults](../../design/config-v2.md#L473)
- **Same artifact with zero modification (local/managed parity & scale-to-zero):** Using the exact same `capsid.json` and `bundle.mjs` (identical SHA-256 digests) on WSL2, local `GET /inventory?sku=7` and managed `GET /@capsid/orders/inventory?sku=7` both returned HTTP 200 with `GET /inventory?sku=7`. The managed worker cycled `0 -> 1 -> 0` and preserved tenant, version, and generation across restart. [Parity target](../../design/config-v2.md#L350)
- **Performance methodology:** In the WSL2 `RelWithDebInfo` managed Host over loopback HTTP with a small source app, resetting the worker to zero between rounds yielded 15/15 successful runs with a median cold request of `10.223 ms` and warm request of `0.519 ms`. The `8.66 / 9.61 / 20.24 ms` reference numbers in the design come from C-ABI bytecode cold starts at different sizes, and `715 / 496 / 127` come from the `v0.3.1-beta.1` 2 GiB density run; these samples do not establish `v0.3.2` Release P99 or density, which require rerunning the formal benchmark protocol on a `v0.3.2` Release build. [Design comparison](../../design/config-v2.md#L401) · [Benchmark methodology](../../reference/benchmarks.md)

Independent probes can be rerun against a Linux Ninja build directory (`$BUILD_DIR`) containing `compile_commands.json`. At the reviewed revision, `within-share` passed while `protected-overshare` and `memory-inheritance` failed with non-zero exit status. [Runner](probes/run_pool_probes.py)
