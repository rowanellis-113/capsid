## 3. New findings

### P0 blockers

No.

### P1 findings

**A capacity qualification rejection will leave a guaranteed minimum slot unallocated.** The configuration is set to minReady=1 and maxWorkers=2. Thread A counts the expanded slot as `replacements_scheduled_` within the pool lock, entering the out-of-lock capacity callback. At this point, Thread B healthily reclaims the only guaranteed worker, and the controller sees that it has been started, setting the guaranteed slot to `needs_replacement`. Now, let the capacity callback return false. The rejection branch only clears its own slot and scheduling count, and returns directly; if there are no factory tasks, it proceeds to the subsequent failure or successful replacement branches. In practice, `ready=0, calls=1, inflight=0, denied=1`, the opposite side can still borrow a slot. Without new requests, the guaranteed worker cannot recover on its own. Existing formal test cases place failures after successful qualification in factories, making it impossible to hit this path.

**Minimum Fix.** Extract the check for guaranteed minimum gaps in active and unisolated pools into the same operation within a single lock. This operation is executed after capacity rejection, startup permission rejection, and factory settlement completion. The existing backoff and concurrency limits continue to be used. Whether to proceed with startup should take into account the real-time state after settlement. Assuming that the capacity rejection callback has already returned and no further requests are sent, it is asserted that the system automatically recovers to a READY state, without overusing the elastic slots. [Scheduling and Qualification 598–645](../../../src/host/generation_pool.cc#L598) · [Record for waiting for replacement: 877–889](../../../src/host/generation_pool.cc#L877) · [Existing licenses reject replacements 1466–1497](../../../src/host/generation_pool.cc#L1466)

### P2 findings

1. **The exit observation callback for the old worker may miss some notifications.** Similarly, block the elastic worker's factory first, reclaim the only guaranteed worker, and wait for the old worker's kExit to be delivered to the event receiver. Then allow the new worker to succeed. In actual testing, with `ready=1, elastic=0, peer=1`, the number of exit observation callbacks for the old worker before retirement was **0**. Reclaiming clears the ready state, and `handle_executor_exit` directly returns. When installing a new worker, it is transitioned to retired state, and the original kExit has been consumed. The production main uses this observation callback to clear the PID sampling cache, and the cleanup may be delayed until the next pruning. Each executor should be marked and the exit observation should be delivered separately. The READY state is only responsible for capacity settlement. The above sequence should assert that there is exactly one notification. [Health Recycling 509–512, Pump Forwarding 1289–1305, Exit Handling 1395–1407, Transfer 1667–1675](../../../src/host/generation_pool.cc#L1395) · [Cache Cleanup 520–525](../../../src/host/main.cc#L520)

2. **The executor that has completed the exit cleanup can still receive late begins.** Obtain the lease first, wait for health recycling to reach the target `exited()==true`, and the handoff request. Actual measurement `exited=1, pending=0, inflight=1, claims=1`. The submission function is first recorded in the queue. The exit flag only prevents writing to the wake-up fd. There are no more working threads to process the queue. Direct submit(begin) also follows the same judgment sequence. The listener has a separate kExit cancellation path. This round demonstrates that the executor accepts unhandled requests, with no observed permanent external HTTP hangs. Within the same executor lock, the commitable state should be checked first. If there is a failure, the lease should be consumed and a clear result should be returned, allowing the caller to complete the request. [Submit directly 240–261, Contract Submission 275–296, Exit Settlement 626–645](../../../src/host/worker_executor.cc#L275) · [Listener exit cleanup 2070–2106](../../../src/host/managed_listener.cc#L2070)

3. **On-demand resampling can still skip a live PID evicted in the prior cycle.** Source counterexample: budget `100 MiB`, watermarks `85/75 MiB`; a previously evicted `20 MiB` process has not yet exited while other processes grow from `75 MiB` to `78 MiB`. The next admission forces resampling, but soft-watermark accounting still applies `recently_evicted_pids_` and exits early at `78 MiB` while the hard check admits at `98 MiB` (`checkInterval = 0` had no background thread clearing the set). Scope `recently_evicted_pids_` to one sampling round (cached recalculations within that cycle only) so fresh on-demand samples re-measure alive retiring PIDs while still keeping them ineligible for eviction. [Admission 431–435, 565–583](../../../src/host/eviction_coordinator.cc#L565) · [Set lifecycle 607–665, 744–750, 756–779](../../../src/host/eviction_coordinator.cc#L624)

4. **Cloning objects containing exceptions silently mutates plain data.** An array with an extra `label='records'` property loses that property; a sparse array of length 3 with only index `2` populated turns its own keys from `2` into `0,1,2`; a custom-class instance holding an `error` property throws `DataCloneError`. The wrapper copied only array indices and forwarded custom-prototype instances directly to the underlying serializer without exception handling. Preserve enumerable own properties and sparse holes during a single graph traversal matching HTML `StructuredSerializeInternal`. [Graph conversion 173–232, array restoration 251–257](../../../js/dom-exception.js#L173) · [HTML StructuredSerializeInternal](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializeinternal)

5. **Invalid transfer lists can prematurely detach the caller's buffer.** Placing the same 3-byte `ArrayBuffer` twice in `transfer` alongside a nested exception succeeded and detached the buffer (length became 0) instead of throwing `DataCloneError` with length preserved at 3; already-detached buffers were also accepted, and `options.transfer` was read twice when cloning nested exceptions. Normalize and validate `transfer` once at entry before serializing and detaching once on both top-level and nested paths. [Wrapper entry 155–165, second call 227–233](../../../js/dom-exception.js#L155) · [Underlying validation/detach 8–29](../../../vendor/txiki.js/src/js/polyfills/structured-clone.js#L8) · [HTML StructuredSerializeWithTransfer](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializewithtransfer)

6. **`getRandomValues` still deviates on shared and detached buffers.** A `Uint8Array` backed by a `SharedArrayBuffer` succeeded, whereas Web Crypto's `ArrayBufferView` parameter lacks `[AllowShared]` and must throw `TypeError`. A 0-byte view is valid, yet passing a detached 0-byte view still threw `TypeError` because Capsid invoked `core.random` for zero-length views. Validate the backing buffer before returning a valid 0-length integer view while preserving `QuotaExceededError` / `TypeMismatchError` / `TypeError` for oversized, floating-point, and non-view inputs. [Crypto entry 82–106](../../../js/bootstrap.js#L82) · [Native random entry 332–353](../../../vendor/txiki.js/src/mod_os.c#L332) · [Web Crypto Algorithm](https://w3c.github.io/webcrypto/#Crypto-method-getRandomValues) · [Web IDL Buffer Conversion](https://webidl.spec.whatwg.org/#es-buffer-source-types)

### P3 suggestions

- **Repeated startup-permit rejections reschedule replacement threads at a fixed interval.** While a floor deficit persists and the permit queue stays full, `abandon()` reschedules at `max(backoff_initial_ms, 10)` without backoff growth or crash-budget consumption, risking tight wake loops across pressured apps. Separate capacity congestion from worker crashes (wait for permit availability or apply bounded backoff). No thread leaks were found. [Retry 1470–1494, thread launch 1131–1151](../../../src/host/generation_pool.cc#L1470) · [Permit rejection 138–152](../../../src/host/managed_admin_backend.h#L138)
- **Formatting gate remained red.** Pinned `clang-format` flagged trailing-comment alignment on `worker_capacity_ledger.h:98-101`. Reformat and rerun the formatting gate (no runtime impact). [worker_capacity_ledger.h 98–101](../../../src/host/worker_capacity_ledger.h#L98)
